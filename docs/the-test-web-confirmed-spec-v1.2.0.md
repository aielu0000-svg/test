## 3. 完了後編集方針A

`completed`のテスト実行では、管理者および割当済み実行者が次の項目だけを変更できる。

- ケース結果
- 実績結果
- 備考
- 証跡の追加
- 証跡画像の新しいバージョンとしての編集
- 証跡の論理削除および復元

次の項目は完了後に変更できない。

- シナリオおよびケースの構成
- ケース順序
- 元定義の再取得
- 実行名、環境、ビルド、予定日時などの実行メタデータ
- 担当者
- 実行日時

許可された更新では、実行ステータスを`completed`のまま維持し、run version、`post_completion_updated_at`、`post_completion_updated_by`を更新する。変更前後とrequest IDを監査ログへ記録する。

## 4. 同時編集と応答順序

### 4.1 楽観ロック

更新対象はversionを持ち、クライアントが取得したversionとDB上のversionが一致する場合だけ更新する。不一致時はHTTP 409を返し、無条件上書きを行わない。

### 4.2 単調versionマージ

ブラウザは、run、run caseその他のversion付きエンティティをAPI応答からstateへ反映する際、現在保持しているversionより小さい応答を破棄する。

複数の保存、証跡更新、一覧更新が異なる順序で完了しても、古い応答によって次を巻き戻してはならない。

- run version
- run case versionと結果
- `post_completion_updated_at`
- `post_completion_updated_by`
- 画面上の保存済み状態

同じversionまたは新しいversionだけを反映する。完了後更新情報が応答で`null`または省略された場合、既に保持している新しい値を消去しない。

### 4.3 409競合復旧UI

409を受け取った画面は、利用者の未保存入力を失わず、次の3操作を明示的に提供する。

1. **最新状態を再読み込み**：サーバーからrun詳細と一覧を再取得する。
2. **現在入力をコピー**：競合発生時の入力をクリップボードへコピーする。ブラウザ権限で失敗した場合は、選択可能なテキストとして表示する。
3. **差分を確認**：現在入力とサーバー最新値について、結果、実績結果、備考、担当者、実行日時の差分を表示する。

最新状態を再読み込みしても、競合時の入力控えは利用者が閉じるか保存に成功するまで保持する。

## 5. 画像編集と失敗時回収

証跡画像編集では、入力画像をSharpで検証し、回転情報を適用したうえで実体をPNGへ再エンコードする。SVG、破損画像、許可していない形式は登録しない。

DB更新または監査処理が失敗した場合、次の生成物を業務データとして残さない。

- 一時アップロードファイル
- PNG本体
- JPEGサムネイル

回収処理自体が失敗した場合は、対象パス、evidence ID、エラー内容を構造化ログへ出力する。回収失敗を黙って無視しない。

## 6. 独立検証の受け入れ条件

GitHub Actions等の独立環境で、少なくとも次を実行する。

- Node.js 20によるTypeCheck
- Unit/APIテスト
- MariaDB 11.4によるMigration・統合テスト
- DB既定照合順序が異なる環境でのMigrationテスト
- Production Build
- Webアプリ起動とreadiness確認
- Chromium E2E
- 409競合復旧UIのブラウザ試験
- DBダンプ、監査ログ、サーバーログ、Playwrightレポートの保存

E2Eを資格情報不足でskip成功にしてはならない。設定不足は明示的な失敗とする。

## 8. Review 10確定変更

本章はv1.1.0以前の同一事項より優先する。Review 10の指摘31、32、33は現行仕様として維持し、それ以外の指摘は本章および実装へ反映する。

### 8.1 プロジェクト削除と名称

- 画面上の「削除」は論理削除ではなく完全削除である。
- 完全削除前にプロジェクトをアーカイブし、確認欄へプロジェクト名を完全一致で入力する。
- 削除理由は任意入力とし、入力する場合は500文字以内とする。
- 完全削除したプロジェクト、テスト定義、実行結果、証跡は復元しない。監査ログは保持する。
- DBレコードの削除確定後、証跡ファイルを回収キューで削除する。ファイル削除失敗は再試行可能な状態で記録する。
- 削除されていないプロジェクト間では同名を許可しない。作成・名称変更の事前検査とDB一意制約の両方で防止する。

### 8.2 完了済み実行の結果変更

`completed`の実行で変更できるケース状態は、次の最終結果だけとする。

- `pass`
- `fail`
- `blocked`
- `skip`

`not_run`または`in_progress`へ戻すことはできない。実行完了前に`not_run`へ戻した場合は、実行日時を残さない。

### 8.3 管理者保護と監査整合性

- 有効な最後の管理者を無効化または実行者へ降格できない。
- 業務更新と対応する監査ログは同一トランザクションで確定する。
- 拒否された操作の監査だけは、業務トランザクション外で独立記録できる。
- JSONまたはExcelのインポート確定要求は二重実行を防止する。

### 8.4 アップロード制限

通常利用を妨げず、サーバー資源枯渇のリスクを抑えるため、1要求につき1ファイル、最大100MiBとする。画像は拡張子や申告MIMEだけでなく実体を検証し、SVGおよび破損画像を拒否する。

### 8.5 Migration

- 適用済みMigrationを変更しない。
- MigrationごとにSHA-256 checksumと状態を保存する。
- 複数Podの同時MigrationはDB名前付きロックで排他する。
- 途中失敗は`failed`として記録し、部分適用の可能性を明示する。
- 適用済みファイルの内容が変わった場合は起動を拒否する。
- 新規DBと、過去Migrationが一部欠落していた既存DBの双方でスキーマ検証を行う。

### 8.6 バックアップと復元

- OpenShift CronJobは`Asia/Tokyo`の毎日02:00に実行する。
- 正常終了したバックアップは原則として最新2世代を保持する。
- バックアップPVC要求容量は220GiBとする。
- DBダンプ、証跡アーカイブ、manifest、checksumを同一バックアップIDで管理する。
- 復元時は、現在状態の復元前バックアップを作成してから、指定した同一世代のDBと証跡を復元する。
- 復元処理中は新規更新を停止し、進行中の更新が完了してからバックアップまたは復元を開始する。
- 管理者画面から手動バックアップおよび復元を要求できる。要求はDBキューへ登録し、CronJobの運用ワーカーが順次処理する。
- 復元後は、復元元世代と復元前世代の2世代を保持する。

### 8.7 証跡・見る場所画像の削除整合性

- DB更新とファイル作成が一体の操作では、DB失敗時に生成ファイルを回収する。
- ファイル削除を先に確定せず、DB側で削除対象を回収キューへ登録してコミットした後にファイルを削除する。
- 保持期限処理には実行証跡だけでなく、見る場所画像も含める。
- 派生画像は元画像を参照できるが、元画像削除時は参照をNULLへ更新し、履歴実行で必要な画像を誤削除しない。

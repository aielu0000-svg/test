# Web UIデザインガイドライン

## 目的と適用範囲

この文書は、`web/src/client`の画面を追加・変更するときの判断基準である。見た目だけを揃えるのではなく、利用者が「現在地」「次の主操作」「結果やエラー」を短時間で判断できる業務画面を目指す。

初期導入では既存のReactと独自CSSを維持する。外部UIライブラリへの全面移行、Impeccableの自動hook、DB/API/Migration変更は含めない。

## 参考にする体系

- [Impeccable](https://impeccable.style/docs): `critique`、`layout`、`audit`、`harden`、`distill`の観点を手動レビューへ使う。skillやhookを必須依存にはしない。
- [Fluent 2 design tokens](https://fluent2.microsoft.design/design-tokens): 色、余白、角丸、影を値の直書きではなく意味ベースのトークンで扱う。
- [Fluent 2 layout](https://fluent2.microsoft.design/layout): 余白と階層で要素の関係を表し、画面幅が変わっても主操作を見失わせない。
- [Ant Design Pro preview](https://preview.pro.ant.design/welcome/): 業務画面のページ見出し、主ナビゲーション、情報カード、フォーム、一覧の構成を参考にする。

参照元の見た目をそのままコピーせず、ザ・テストの用語、既存操作、権限、レスポンシブ要件に合わせる。

## 基本原則

1. 1画面の主目的を1つにする。主操作は原則1つを強調し、補助操作と危険操作を視覚的に分ける。
2. ヘッダー、主ナビゲーション、ページ見出し、本文、カード内見出しの順で階層を作る。
3. 色だけで状態や役割を伝えない。ラベル、記号、配置、`aria-*`、説明文を併用する。
4. 高密度の業務データは隠しすぎない。段階表示は、低頻度の説明や詳細設定に使う。
5. 既存の動作、用語、権限、API契約をデザイン都合で変えない。

## トークン

共通トークンは`web/src/client/styles.css`の`:root`を正とする。

- 色: `--color-bg-*`、`--color-text-*`、`--color-border-*`、`--color-brand-*`、状態色を使う。
- 余白: 4px基準の`--space-1`から`--space-16`を使う。新規実装で中間的な余白値を増やさない。
- 角丸: コントロール、カード、パネルの3段階を基本にする。ピル形状は状態バッジなど用途が明確な要素に限定する。
- 影: 通常パネルとオーバーレイを区別する。カードごとに異なる影を増やさない。
- フォーカス: `:focus-visible`を消さない。背景色に関係なく認識できるアウトラインを維持する。

画面固有CSSの変数は、可能な限り共通トークンの別名として定義する。既存の生値は、触れた範囲から段階的に置き換える。

## ページ構成

### アプリとプロジェクトのナビゲーション

- 最上部は製品/プロジェクト名、利用者、権限、終了操作を置く。
- 直下の主ナビゲーションは現在地を背景と`aria-current="page"`の両方で示す。
- 横幅が足りない場合はナビゲーションを横スクロール可能にし、項目名を途中で折り返さない。

### ページ本文

- 本文幅は通常`--content-width`、高密度のプロジェクト画面は`--workspace-width`を上限にする。
- ページ先頭に見出し、短い説明、必要なら主操作を置く。
- 同格の情報はカードまたはグリッドでまとめる。カードの入れ子は原則1段までにする。
- 2列レイアウトは狭い幅で1列へ落とす。固定幅ではなく`minmax()`を使い、本文側へ`min-width: 0`を付ける。

### フォームと表

- ラベルをplaceholderで代用しない。必須/任意とエラーは入力欄の近くに表示する。
- 保存、実行、追加、複製、表示切替、取込の既存アクション階層を維持する。
- 横に長い表は内容を潰さずスクロール領域にする。狭い画面では編集対象や主操作が画面外に固定されないよう確認する。

## 手動デザインレビュー

UI変更ごとに、次の順で確認する。Impeccableの自動実行を前提にしない。

1. Shape: 対象利用者、画面の目的、最も重要な1操作、変えてはいけない業務仕様を書く。
2. Critique: 視線順、情報階層、用語、認知負荷、主操作の競合を確認する。
3. Layout: 320px前後、650px、850px、1120px以上で重なり、不要な横スクロール、切れを確認する。
4. Audit: キーボード操作、フォーカス、ラベル、コントラスト、現在地、disabled/error/loading状態を確認する。
5. Harden: 長い日本語、0件、大量件数、通信失敗、閲覧のみ、権限差、テキスト拡大で崩れないか確認する。
6. Distill: 重複説明、競合するボタン、不要な枠線や装飾を減らす。

問題はP0（操作不能/データリスク）、P1（主要導線の誤認/アクセシビリティ阻害）、P2（不整合/冗長）、P3（微調整）で記録し、優先度順に直す。

## 完了条件

- 主操作、現在地、成功/警告/エラーが色以外でも判別できる。
- キーボードで到達でき、フォーカス位置が見える。
- 既存の主要E2Eに加え、変更画面の現在地または主操作を回帰テストで固定する。
- TypeCheck、Unit/API、Production Build、対象E2Eの結果を`docs/TASK_LOG.md`へ記録する。
- レイアウト/依存関係が変わる場合は`docs/codemap`を更新する。

## 外部コンポーネント導入の判断

RadixなどのヘッドレスUIは、今後新しいダイアログ、メニュー、コンボボックス等を作る際に、独自実装よりアクセシビリティと状態管理のリスクを下げられる場合だけ個別採用を検討する。既存画面の一括置換は行わず、依存追加時はbundle、保守性、キーボード操作、E2Eへの影響をIssueで評価する。

# Codex開発・運用ルール

版: 1.0  
適用対象: 本リポジトリで作業するCodexおよびその他の実装担当者

---

## 1. このルールの目的

この文書は、次を防止するための必須ルールです。

- 適用済みマイグレーションの改変
- DB履歴と実スキーマの不一致
- UIだけ直して実処理を検証しない状態
- テスト未実施なのに完了扱いすること
- 過去のレビュー指摘の取りこぼし
- 同じ不具合の再発
- 作業内容、原因、結果が追跡できない状態
- 未解決課題の放置

Codexは作業開始時にこの文書を読み、作業完了まで遵守してください。

---

# 2. 必須管理ファイル

リポジトリ内に次を作成し、継続更新してください。

```text
docs/ISSUE_LEDGER.md
docs/TASK_LOG.md
docs/OPEN_ISSUES.md
docs/AI_REVIEW_HISTORY.md
```

ファイルが存在しない場合、最初の作業で作成してください。

これらの更新は任意ではありません。コード変更と同じ作業単位で更新してください。

---

## 3. 課題管理台帳

ファイル:

```text
docs/ISSUE_LEDGER.md
```

### 目的

不具合、仕様変更、改善、技術的負債、セキュリティ課題、運用課題を一元管理します。

### 必須列

```markdown
| ID | 登録日時 | 種別 | 優先度 | 状態 | 対象 | 内容 | 再現手順 | 原因 | 対応方針 | 対応結果 | 検証 | 関連ファイル | 関連レビュー |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
```

### ID形式

```text
ISSUE-YYYYMMDD-NNN
```

例:

```text
ISSUE-20260801-001
```

### 種別

```text
Bug
Security
Data
Migration
UI
UX
Specification
Performance
Test
Operation
TechnicalDebt
```

### 優先度

```text
P0: リリース阻止
P1: 高
P2: 中
P3: 低
```

### 状態

```text
Open
Investigating
In Progress
Blocked
Ready for Verification
Verified
Closed
Rejected
Deferred
```

### 運用ルール

- 課題を認識した時点で登録する
- 原因未確定の段階で推測を事実として記載しない
- 修正開始時に`In Progress`へ変更
- 実装完了だけでは`Closed`にしない
- 必要なテストが成功したら`Verified`
- 利用者確認または受け入れ条件達成後に`Closed`
- 未実施の検証を「成功」と書かない
- 別の問題を発見した場合、同じ行へ混ぜず新規課題を作る
- Deferredには理由と再検討条件を記載する

## 4. タスク実績ログ

ファイル:

```text
docs/TASK_LOG.md
```

### 目的

タスクごとに「何が起きたか」「何を調べたか」「何を変更したか」「何が残ったか」を記録します。

### 必須記載

各タスクの開始時と完了時に追記してください。

```markdown
## TASK-YYYYMMDD-NNN: タスク名

- 開始日時:
- 完了日時:
- 対応課題:
- 担当:
- 状態:

### 作業前の状態

- 発生していた現象:
- 再現手順:
- 期待動作:
- 実際の動作:
- 関連エラーID:
- 関連ログ:

### 調査内容

- 確認したファイル:
- 確認したDB:
- 実行したコマンド:
- 仮説:
- 仮説の検証結果:
- 確定原因:

### 実施内容

- 変更ファイル:
- DB変更:
- Migration:
- API変更:
- UI変更:
- テスト追加:
- ドキュメント更新:

### 作業中に発生したこと

- 新たに発生したエラー:
- 想定外の影響:
- 追加で判明した課題:
- 回避策:

### 検証

- TypeCheck:
- Unit Test:
- Integration Test:
- Build:
- E2E:
- 手動確認:
- DB確認:
- セキュリティ確認:

### 結果

- 解消した内容:
- 解消していない内容:
- 残るリスク:
- 次のタスク:
```

### 必須ルール

- タスクをこなすごとに必ず追記する
- 成功だけでなく、失敗、やり直し、追加エラーも記録する
- 実行していないテスト欄には`未実施`と明記する
- 「問題なし」だけで終わらせず、確認方法を書く
- コマンドは実際に実行したものだけを書く
- 変更していないファイルを記載しない
- タスクの途中で方針変更した場合、その理由を残す

## 5. 未解決課題

ファイル:

```text
docs/OPEN_ISSUES.md
```

### 目的

現在残っている問題を、優先順位順に確認できるようにします。

### 形式

```markdown
# Open Issues

## P0

- [ ] ISSUE-... 内容
  - 影響:
  - 暫定回避:
  - 完了条件:

## P1

...

## Blocked

- [ ] ISSUE-...
  - ブロック理由:
  - 必要な情報:
```

### ルール

- `ISSUE_LEDGER.md`でOpen系状態の課題を同期する
- 完了済み課題を残さない
- 各項目に完了条件を記載する
- 毎回の作業完了時に見直す

---

## 6. AIレビュー履歴

ファイル:

```text
docs/AI_REVIEW_HISTORY.md
```

### 目的

review1、review2のような外部レビュー指摘と対応状況を追跡します。

### 形式

```markdown
## Review 7

- 実施日:
- 入力ソース:
- 総評:

| 指摘ID | 優先度 | 指摘 | 課題ID | 対応状況 | 検証結果 |
|---|---|---|---|---|---|
```

### ルール

- レビュー指摘を要約しすぎて意味を変えない
- 各指摘を課題IDへ関連付ける
- 未対応、部分対応、対応済み、検証済みを区別する
- コード上で対応しただけなら`対応済み・未検証`
- 実動作確認後に`検証済み`
### 6.1 codex-reviewの利用条件

- `codex review --uncommitted` は原則として使用しない。
- `codex-review`を実施する場合は、レビュー対象ファイルを明示して確認し、機密情報が含まれていないことを確認したうえで、対象差分をコミットまたはベースブランチとの差分として実行する。
- Codexサービスへのリポジトリ内容の送信は、ユーザーの明示的な承認がある場合に限る。本タスクではWeb版コードの外部送信が承認されている。
- レビュー対象にはElectron版を含めず、Web版の実装、Migration、テスト、API仕様、デプロイ設定だけを含める。
- `codex review --commit <SHA>` または `codex review --base <BRANCH>` を使用し、レビュー結果を `docs/AI_REVIEW_HISTORY.md` と `docs/TASK_LOG.md` に記録する。
- 外部送信の承認がない場合、または安全制約で実行できない場合は、ローカル差分確認、仕様照合、TypeCheck・単体テスト・統合テスト・ビルド・E2E・手動確認による代替レビューへ切り替える。

# 7. マイグレーションルール

## 7.1 適用済みファイルは変更禁止

一度共有環境、開発DB、検証DB、本番DBのいずれかへ適用したマイグレーションは変更禁止です。

禁止例:

```text
008_ui_workflow.sqlへ後から列追加
```

正しい例:

```text
011_repair_ui_workflow_columns.sqlを追加
```

---

## 7.2 必ず連番の新規ファイル

DB変更は必ず新規Migrationで行います。

```text
001
002
...
010
011
012
```

ファイル名は変更内容が分かる名称にしてください。

---

## 7.3 冪等性を考慮

既存環境の補修Migrationでは、必要に応じて以下を使用してください。

```sql
ADD COLUMN IF NOT EXISTS
CREATE TABLE IF NOT EXISTS
CREATE INDEX IF NOT EXISTS
```

外部キーは`information_schema`で存在確認してください。

---

## 7.4 Migrationにデータ破壊を含めない

次の操作は、明示的な承認なしに実行禁止です。

```text
DROP DATABASE
DROP TABLE
TRUNCATE
列削除
大量DELETE
不可逆な型変更
```

必要な場合は次を提示してください。

- 影響範囲
- バックアップ方法
- ロールバック方法
- 停止時間
- データ変換方法

---

## 7.5 新規DBと既存DBを両方検証

DB変更時は必ず次を検証してください。

### 新規DB

```text
空DB
→ 全Migration
→ Schema Validation
→ 起動
→ 主要API
```

### 既存DB

```text
前バージョンDB
→ 新Migration
→ Schema Validation
→ 起動
→ 既存データ確認
```

---

## 7.6 起動時Schema Validation

Migration履歴だけでなく実スキーマを検証してください。

確認対象:

- 必須テーブル
- 必須列
- 必須インデックス
- 必須外部キー
- 文字コード
- 照合順序

不足時はready状態にしないでください。

---

# 8. コード変更ルール

## 8.1 既存仕様との照合

変更前に次を確認してください。

```text
SPEC.md
the-test-web-confirmed-spec-v1.0.0.md
the-test-web-confirmed-spec-v1.1.0.md
the-test-web-confirmed-spec-v1.2.0.md
PROGRESS.md
改善点.md
SECURITY_ASSESSMENT.md
docs/ISSUE_LEDGER.md
docs/OPEN_ISSUES.md
docs/AI_REVIEW_HISTORY.md
```

仕様と実装が食い違う場合は、勝手に仕様を変えず課題として登録してください。

---

## 8.2 旧実装を残さない

新UIへ完全移行した場合、到達不能な旧UI、旧API、旧state、旧分岐を削除してください。

互換性のために残す場合は、用途、削除予定、テスト範囲を明記してください。

---

## 8.3 巨大コンポーネントを避ける

目安として、1コンポーネントが500行を大きく超える場合は分割を検討してください。

責務例:

```text
RunCreatePanel
RunPreparationPanel
FocusedRunPanel
CompletedRunPanel
EvidencePanel
FolderTree
ScenarioEditor
CaseDetailPanel
```

行数だけで機械的に分割せず、状態と責務を基準にしてください。

---

## 8.4 状態競合を考慮

以下を必ず検討してください。

- 古いAPIレスポンス
- 並行保存
- 自動保存
- 親の再取得
- version更新
- 409競合
- 画面遷移中の未保存入力
- コンポーネント再マウント

最新入力を古いデータで上書きしないテストを追加してください。

---

## 8.5 エラー表示

SQL、スタックトレース、内部パスを利用者画面へ表示しないでください。

画面には次を表示します。

```text
利用者向け説明
再試行方法
エラーID
```

詳細はサーバーログへ記録します。

---

# 9. セキュリティ・ファイル処理

## 9.1 アップロード値を信用しない

- MIMEタイプを信用しない
- 拡張子を信用しない
- 画像はデコーダで実体検証
- パストラバーサルを防止
- 保存ファイル名はサーバー生成
- SVGは拒否または安全化
- 失敗時に一時ファイルを削除

---

## 9.2 権限はAPIで検証

UI上の非表示だけで権限を実現しないでください。

プロジェクト割当、編集、証跡、実行完了後更新、エクスポートはAPI側で権限確認してください。

---

## 9.3 監査ログ

次を監査ログへ記録してください。

- 誰が
- いつ
- 何を
- 変更前
- 変更後
- 対象プロジェクト
- 対象実行
- 完了後更新か

---

# 10. テストルール

## 10.1 必須検証

変更内容に応じて、次を実行してください。

```text
TypeCheck
Unit Test
Integration Test
Production Build
Playwright E2E
手動確認
DBスキーマ確認
```

---

## 10.2 E2Eをskipしない

環境変数不足を理由にE2Eをskipしないでください。

必要なテスト用ユーザー、プロジェクト、データはセットアップで作成してください。

実行件数0件を成功扱いにしないでください。

---

## 10.3 実行していない検証を成功と報告しない

次を区別してください。

```text
収集成功
起動成功
テスト本走成功
一部成功
未実施
失敗
```

Playwrightの収集成功だけで「E2E成功」と記載しないでください。

---

## 10.4 失敗成果物

E2E失敗時は次を保存してください。

- スクリーンショット
- 動画
- trace
- APIレスポンス
- request ID
- 関連サーバーログ

---

## 10.5 DB変更時の統合テスト

Migration、Repository、SQL、保存APIを、実際のMariaDBに対して検証してください。

モックだけで完了としないでください。

---

# 11. タスク実行手順

Codexは各タスクで次の順番を守ってください。

## 開始前

1. このルールを読む
2. 仕様書を確認する
3. ISSUE_LEDGERを確認する
4. OPEN_ISSUESを確認する
5. 新規課題または既存課題を特定する
6. TASK_LOGへ開始記録を書く
7. 受け入れ条件を明確にする

## 調査

1. 再現する
2. ログを確認する
3. DBを確認する
4. 原因仮説を作る
5. 仮説を検証する
6. 原因を台帳へ記録する

## 実装

1. 最小限の変更方針を決める
2. Migrationが必要か確認する
3. 実装する
4. テストを追加する
5. 旧実装を整理する

## 検証

1. TypeCheck
2. Unit Test
3. Integration Test
4. Build
5. E2E
6. DB確認
7. セキュリティ確認
8. 受け入れ条件確認

## 完了時

1. ISSUE_LEDGERを更新
2. TASK_LOGへ結果を記入
3. OPEN_ISSUESを更新
4. AI_REVIEW_HISTORYを更新
5. 残課題を明示
6. 実施していない検証を明示
7. 変更ファイルとテスト結果を報告

---

# 12. 完了の定義

次のすべてを満たした場合のみ、タスクを完了としてください。

- 原因が記録されている
- 修正が実装されている
- 必要なテストが追加されている
- 必須テストが成功している
- 受け入れ条件を満たしている
- DB変更が新旧環境で検証されている
- 課題管理台帳が更新されている
- タスクログが更新されている
- 未解決課題がOPEN_ISSUESへ反映されている
- レビュー指摘の対応状況が更新されている
- 残るリスクが明記されている

コードを書いただけ、ビルドが通っただけ、テストを収集できただけでは完了ではありません。

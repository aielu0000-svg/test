# P1: 必須修正

## 3. BIGINTのJSON化を全経路で統一する

### 対応課題

`ISSUE-20260803-001`

### 現象

証跡一覧では`byte_size`をNumberへ変換していますが、次の経路ではMariaDBの`BIGINT`が未変換のままJSONレスポンスに含まれる可能性があります。

- `GET /api/evidence/:id/versions`
- 正式JSONエクスポート

既に証跡一覧で、`BIGINT`の直接JSON化による500が発生しています。同じ障害を別APIで再発させないでください。

### 必須対応

- DBレスポンスの数値正規化処理を共通化する。
- `byte_size`のAPI表現を明確に決める。
  - JavaScriptの安全整数範囲を保証できるならNumberへ変換する。
  - 保証できない場合は文字列としてOpenAPIと正式JSONスキーマへ定義する。
- 証跡一覧、証跡バージョン、正式JSONエクスポートで同じ表現を使用する。
- 他の`BIGINT`列もJSON化経路を検索し、同じ問題がないか確認する。

### 必須テスト

- 実MariaDBへ証跡を登録する。
- versions APIが200で返ることを確認する。
- 証跡を含む正式JSONエクスポートが200で返ることを確認する。
- 応答スキーマと値の型を検証する。

## 4. 合格率を確定仕様へ統一する

### 対応課題

`ISSUE-20260803-002`

### 確定ルール

```text
合格率 = pass / (pass + fail + blocked)
```

- `skip`は分母に含めない。
- `not_run`、`in_progress`も分母に含めない。
- 分母が0件の場合の表示値を仕様化する。

### 必須対応

- サーバーのドメイン関数を確定ルールへ修正する。
- ダッシュボードSQLを確定ルールへ修正する。
- クライアント側の独自計算を廃止するか、同じ共通ルールへ合わせる。
- blockedを分母から除外している既存Unit Testを修正する。
- API、ダッシュボード、実行詳細で同じ値になるよう統一する。

### 必須テスト

最低限、次の組合せをテストしてください。

| pass | fail | blocked | skip | not_run | 期待値 |
|---:|---:|---:|---:|---:|---:|
| 1 | 0 | 0 | 0 | 0 | 100% |
| 1 | 1 | 0 | 0 | 0 | 50% |
| 1 | 0 | 1 | 0 | 0 | 50% |
| 1 | 1 | 1 | 1 | 1 | 約33.33% |
| 0 | 0 | 0 | 3 | 2 | 仕様化した0件時表示 |

実MariaDBのAPI集計と画面表示も確認してください。

## 5. 409競合時の復旧と古いレスポンス対策を実装する

### 対応課題

`ISSUE-20260803-003`

### 必須対応

#### 5.1 run versionを単調増加でマージする

- ケース結果保存レスポンス
- 証跡追加・更新レスポンス
- 親コンポーネントによる再取得
- 完了後更新レスポンス

これらを親の実行stateへ反映するとき、現在より古い`test_runs.version`を破棄してください。

新しいversionのレスポンス後に古いレスポンスが返っても、次が巻き戻らないようにしてください。

```text
test_runs.version
post_completion_updated_at
post_completion_updated_by
ケースの最新入力
```

#### 5.2 409専用の復旧UIを追加する

一般的なエラー表示だけで終わらせず、少なくとも次を提供してください。

```text
最新状態を再読み込み
現在の入力をコピーして保持
差分を確認
```

「差分を確認」は、サーバー側最新値と現在入力の差が利用者に分かる表示にしてください。

### 必須テスト

PlaywrightまたはAPIモックで次を実行してください。

1. 先行保存リクエストを意図的に遅延する。
2. 後続リクエストを先に成功させる。
3. 新しいversionを画面へ反映する。
4. 遅延した古いレスポンスを返す。
5. 最新入力、更新者、更新日時、versionが戻らないことを確認する。
6. 409発生時に3つの復旧操作が利用できることを確認する。

ケース切替、証跡追加、親再取得と並行した場合も検証してください。

## 6. 画像クリーンアップ失敗を再試行可能にする

### 対応課題

`ISSUE-20260803-004`

### 現在の問題

DBレコードを削除した後にファイル削除エラーを握り潰すと、実ファイルだけが残り、その後のクリーンアップで追跡できなくなります。

### 必須対応

- ファイル削除失敗を成功扱いしない。
- DBレコードを先に消して追跡不能にしない。
- 削除保留状態、削除ジョブ、または再試行可能な状態を設ける。
- 参照中ファイルは削除しない。
- ファイル削除成功後にDBレコードを削除するか、整合性を保てる補償処理を設計する。
- 次を構造化ログへ記録する。

```text
処理件数
削除成功件数
参照保持件数
削除失敗件数
対象ID
保存先
エラー内容
request IDまたはjob ID
```

### 必須テスト

- 参照なし・削除成功
- 他ケースから参照中
- 過去実行スナップショットから参照中
- ファイル削除失敗
- DB更新または削除失敗
- 再試行後の成功

実ファイルとDBレコードの両方を確認してください。

## 9. 編集画像を必ずPNGへ再エンコードする

### 対応課題

`ISSUE-20260803-007`

### 必須対応

編集画像バージョンを`.png`へrenameするだけではなく、Sharp等で実際にPNGへ再エンコードしてください。

例:

```ts
await sharp(temporaryPath).png().toFile(destination);
```

- Content-Type、拡張子、ファイル実体を一致させる。
- 許可する入力形式を明示する。
- SVGを拒否するか、安全なラスタライズ方針を仕様化する。
- 変換失敗時に一時ファイルと出力途中ファイルを削除する。

### 必須テスト

- JPEG入力からPNG実体を生成する。
- WebP入力からPNG実体を生成する。
- SVGを方針どおり拒否または変換する。
- 破損画像を拒否する。
- 出力画像を再解析し、実体がPNGであることを確認する。

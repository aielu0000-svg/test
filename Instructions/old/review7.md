# 最優先の問題

## 1. テスト実行不能はリリース阻止レベル

ユーザー確認済みの「テスト実行できない」は、最優先で直す必要があります。

現在の導線は、

1. テスト設計から「テスト実行へ」
2. 対象シナリオを初期選択
3. 実行情報を入力
4. 実行レコードを作成
5. 実行開始
6. ケース結果を入力

という構成です。

UIとしては改善されていますが、状態管理が複雑です。

`RunsPanelV2`では、次の状態を同時に持っています。

* 選択中実行
* 実行詳細
* 選択シナリオ
* 選択ケース
* 選択データセット
* 実行メタ情報
* 改訂対象
* 初期シナリオID

さらに`refresh()`が実行一覧と詳細を再取得し、複数のローカル状態を上書きします。

この構成は、次の不具合を発生させやすいです。

* シナリオを選択した直後に再読み込みで選択が消える
* 新規作成中と既存実行選択中の状態が混在する
* API成功後に古い状態で再描画される
* 実行開始時に対象ケースが空になる
* 初期シナリオIDが画面遷移後に正しく反映されない

### 修正方針

新規実行フォームと既存実行詳細を別コンポーネントに分離してください。

```text
RunCreatePanel
RunPreparationPanel
FocusedRunPanel
CompletedRunPanel
```

少なくとも、「新規作成中」と「既存実行の編集」を同じstate群で管理しない方が安全です。

---

## 2. テスト結果が元に戻る問題は、まだ再発しやすい

結果入力画面では、ケースの`id`または`version`が変わるたびにローカル入力値をサーバー値で再初期化しています。

```tsx
useEffect(() => {
  setStatus(item.status);
  setActualResult(item.actual_result ?? "");
  ...
}, [item?.id, item?.version]);
```

保存後、親コンポーネントがAPIレスポンスをケース一覧へ反映すると`version`が上がります。その時点で入力値が再設定されます。

正常時は保存値と同じなので問題ありませんが、次の場合に利用者の入力が消える可能性があります。

* 保存中に追加入力した
* 古い保存レスポンスが後から返った
* 証跡登録など別処理でケース一覧が再取得された
* 複数保存が並行した
* 親側の再読み込みが古い値を返した

### 修正方針

* 保存要求ごとに連番を付ける
* 最新要求より古いレスポンスを破棄する
* 編集中は外部更新でフォーム値を上書きしない
* `version`変更だけで無条件にフォームを初期化しない
* ケースIDが変わった時だけ初期化する
* 保存後はAPIレスポンスと現在入力を比較して反映する

次のような状態が必要です。

```ts
lastSubmittedRevision
lastResolvedRevision
isEditing
```

現在のコードは明示保存方式なので以前より安全ですが、**競合防止としてはまだ不十分**です。

---

## 3. 証跡機能はUIとサーバー仕様が噛み合っていない可能性が高い

証跡画面自体は改善されています。

* 結果入力欄の近くに配置
* ファイル選択
* クリップボード貼り付け
* アップロード進捗
* エラーID
* サムネイル
* 画像編集

ただし、実装上は不安要素があります。

### 問題1：画面上の説明と実装が矛盾

UIには、

> サイズ・件数・拡張子のアプリ独自上限は設けない

と表示されています。

一方、Fastify本体には次があります。

```ts
bodyLimit: 25 * 1024 * 1024
```

multipart設定では無制限を指定していますが、実運用ではRoute、プロキシ、OpenShift、Fastifyなど複数層の制限を受けます。

「無制限」と表示するのは危険です。

### 問題2：失敗後の一時ディレクトリが残る

アップロード処理で失敗した場合、

* `.uploading`ファイル
* 保存済みファイル

は削除します。

しかし、作成済みの証跡用ディレクトリ自体は削除していません。失敗が続くと空ディレクトリが残る可能性があります。

### 問題3：クリップボードAPIの利用条件

`navigator.clipboard.read()`は、一般に次の条件の影響を受けます。

* HTTPSまたはlocalhost
* ブラウザ権限
* 利用者操作から直接呼び出されること
* ブラウザ対応状況

エラー時に「クリップボードに画像がありません」としか出ない場合、権限拒否との区別がつきません。

### 問題4：画面にケース選択が重複

`FocusedRunPanel`では現在のケースが既に決まっています。それにもかかわらず、内部の証跡パネルで再び「関連するテストケース」を選ばせています。

これは誤添付の原因になります。

### 推奨

結果入力画面ではケース選択を非表示にし、現在ケースへ固定してください。

# テスト設計画面の追加問題

## 1. フォルダ操作がまだ「エクスプローラー」ではない

ツリー、ドラッグ＆ドロップ、右側メニューは追加されています。

しかし、次の点はWindowsエクスプローラー的ではありません。

* 新規フォルダを常設入力欄で作る
* 名前変更に`window.prompt`を使う
* 削除理由にも`window.prompt`を使う
* フォルダの展開・折りたたみ状態が明確でない
* 複数選択がない
* キーボード操作がない
* 右クリックメニューではなく`details`中心
* ドラッグ中の移動先表示が弱い
* パンくずがない
* フォルダ名が同一階層で重複した場合の扱いが不明

### 推奨

* F2またはインライン編集
* 右クリックコンテキストメニュー
* ドロップ先ハイライト
* 展開三角
* 選択フォルダの背景強調
* パンくず
* Deleteキー
* Enterで開く
* Escで編集取消
* フォルダ作成は「＋」ボタンからインライン生成

---

## 2. ケースの複数フォルダ所属仕様を失っている

元仕様では、テストケースは複数フォルダへ所属可能です。

現在の右詳細ではフォルダ選択が単一の`select`です。

```tsx
folderIds: event.target.value ? [event.target.value] : []
```

これは、複数フォルダ所属を単一所属に縮退させています。

既存ケースを読み込んでフォルダを変更すると、ほかの所属フォルダが消える可能性があります。

### 修正

* チェックボックス式
* 複数選択リスト
* タグ形式

のいずれかで複数フォルダを保持してください。

これは仕様後退です。

---

## 3. 見る場所画像がDBファイル管理ではなくData URL保存

テスト設計画面では、画像をFileReaderでData URLに変換し、シナリオ保存JSONへ含めています。

制限は次のとおりです。

* 1ケース5枚
* 1枚3MB程度
* Data URLとしてJSON送信
* 対応形式限定

これは確定仕様の「アプリ独自のサイズ・件数上限を設けない」「ストリーミング保存」と矛盾します。

また、画像をJSON本文に含めるため、

* メモリ消費増大
* API bodyLimit超過
* Base64による約33%増加
* 保存処理全体の失敗
* 大量ケース保存時のタイムアウト

につながります。

### 修正

見る場所画像も証跡と同じファイルAPIへ分離してください。

```text
一時アップロード
→ ファイルID取得
→ テスト全体保存でファイルIDを関連付け
```

---

## 4. 自動伸長は初期表示時に不完全な可能性

`grow()`は入力イベント時には呼ばれます。

ただし、既存シナリオを読み込んだ直後のtextareaに対して、全項目へ明示的に再計算する処理が見当たりません。

ブラウザやCSSによっては、読み込んだ長文が初期高さのまま見切れる可能性があります。

### 修正

rowsや選択ケースが変わった後に、対象textareaをまとめて伸長してください。

---

## 5. 保存後の画面状態と一覧更新に競合の余地

保存処理の最後で`onChanged()`を実行し、親側で一覧を再取得します。

その間に現在選択中のシナリオのversionや一覧情報が更新されます。

ローカル側でも保存レスポンスからversionを反映しているため、親再取得とローカル更新の二重経路があります。

現時点で必ず壊れるとは断定できませんが、競合しやすい構成です。

# テスト実行UIの追加問題

## 1. 完了済み実行が編集不可になっている

確定仕様では、完了済み実行も編集可能とし、「完了後更新あり」を表示する方針でした。

しかし現在は、完了状態では結果入力、証跡、担当者、日時が無効化されています。

```tsx
disabled={!canEdit || runStatus === "completed"}
```

サーバー側も完了済みを変更不可にしています。

```ts
if (!isRunMutable(parentStatus)) ...
```

これは確定仕様との明確な不一致です。

### 必要な対応

* 完了後編集を許可
* 完了後更新フラグ
* 最終更新者
* 最終更新日時
* 監査ログ
* 完了後編集であることの警告表示

---

## 2. シナリオ結果とケース結果の二重入力が残る

コードには`RunScenarioRow`と`RunCaseRow`が残っています。

新しい集中実行画面とは別に、シナリオ単位・ケース単位の結果入力UIが存在します。

シナリオ状態はケース結果から自動算出する仕様だったため、利用者が直接シナリオ状態を変更できる構成は不整合を起こし得ます。

### 修正

シナリオ状態は原則表示専用にしてください。

手動変更を残すなら、用途と優先順位を仕様化する必要があります。

---

## 3. 実行完了判定が弱い

最後のケースで「テストを完了」ボタンが表示されますが、全ケースが実行済みかを画面側で厳密に判定しているようには見えません。

少なくとも表示条件は、

* 実行中
* 最後のインデックス
* 未保存でない

だけです。

未実行ケースが残っていても、最後のケースへ移動すれば完了操作が可能な可能性があります。

### 修正

完了前に次を検証してください。

* 未実行件数
* 必須実績結果
* 保存失敗
* 証跡アップロード中
* 除外扱い
* スキップ理由

完了確認画面に集計を出すべきです。

---

## 4. 「保存して次へ」で保存後のケースversion更新と移動が競合

`saveCurrent(true)`は、親の`onSave`完了後にindexを進めます。

その一方で親側ではケース一覧を更新し、子側のeffectが動きます。

現在ケースと次ケースの描画タイミングによっては、保存状態表示が不自然になったり、次ケースの初期化が遅れる可能性があります。

E2Eで連続5〜10ケースを高速入力する試験が必要です。

# ログアウト

コード上では以前より改善されています。

* APIへPOST
* サーバーセッション破棄
* Cookie解除
* React状態解除
* ログイン画面へ戻す
* E2Eで`/api/auth/me`が401になることを確認する予定

ただし、ユーザー側で「ログアウトできない」と確認されているため、コード上の実装だけでは合格にできません。

考えられる原因は次です。

* フロントとAPIが別オリジンでCookie条件が不一致
* Viteプロキシ設定
* `SameSite`や`Secure`
* localhostとIPアドレスの混在
* APIエラーでstateを消していない
* 古いフロント資産を表示している
* Service Workerやキャッシュ
* Dashboard側とWorkspace側でログアウト処理が異なる

特にDashboard側とWorkspace側で別のログアウト関数を使っているため、共通化すべきです。

現状のE2Eは1本だけです。

このため、CIで実質何も検証せず成功する可能性があります。

1. ログイン・ログアウト
2. 新規テスト作成
3. 既存テスト編集
4. 複数行貼り付け
5. フォルダ作成・移動・名前変更
6. 実行作成
7. シナリオ選択
8. 実行開始
9. 合格保存
10. 不合格＋実績結果保存
11. 連続ケース入力
12. 証跡ファイル追加
13. クリップボード画像追加
14. 割当
15. 割当解除

環境変数がない場合に全E2Eがskipされる構成は、品質ゲートとして弱すぎます。

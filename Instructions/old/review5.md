## 全体レビュー

### 「現場の誰でも使えるテスト管理ツール」という観点

コードと画面構成を確認した限り、現状は**機能はかなり揃っている一方、業務用の管理ツールとしての概念がまだ前面に出すぎています**。

現場の利用者が考えるのは、通常次の流れです。

```text
何を確認するか決める
↓
確認内容を作る
↓
実行する
↓
結果と証跡を残す
↓
報告する
```

一方、現在の画面は次の概念を理解しないと使いこなせません。

* テストケース
* シナリオ
* データセット
* フォルダ
* 手順書
* Excel取込
* 入出力
* スナップショット
* 実行定義

この差が、初めて使う人にとっての難しさになっています。

---

# 1. 最初に表示する言葉を業務目線にする

現状のタブは概ね次の構成です。

* 一括編集
* テスト実行
* 手順書
* Excel取込
* 入出力
* ごみ箱

以前より整理されていますが、「一括編集」は利用者の目的を表していません。

利用者は一括編集をしたいのではなく、**テストを作成したい**から画面を開きます。

## 推奨名称

| 現在      | 推奨        |
| ------- | --------- |
| 一括編集    | テスト設計     |
| テスト実行   | テスト実行     |
| 手順書     | 作業手順      |
| Excel取込 | Excelから追加 |
| 入出力     | エクスポート・移行 |
| ごみ箱     | 削除済み      |

「テスト設計」の中で、シナリオとケースをまとめて扱う形が自然です。

---

# 2. 初回利用者向けの開始画面が必要

プロジェクトを開いた直後に編集表を表示すると、初めて使う人は何から始めるべきか判断できません。

プロジェクト内の最初の画面には、短い開始案内を置くのがよいです。

```text
このプロジェクトで行うこと

1. テストを作成する
2. テストを実行する
3. 結果を確認する
```

その下に大きな操作ボタンを置きます。

```text
＋ 新しいテストを作る

▶ 作成済みテストを実行する

📄 Excelから取り込む
```

ただし、毎回この案内を見せる必要はありません。
既にシナリオが存在する場合は、最近編集したシナリオや実行中テストを表示した方が便利です。

---

# 3. 「テストケース」と「シナリオ」の関係を利用者に意識させすぎない

現在の設計では、テストケースとシナリオが別の定義として扱われています。DB上では問題ありませんが、画面上では難しく見えます。

## 利用者向けの考え方

画面上では次のように見せるのが適切です。

```text
テスト：ログイン機能の確認

確認項目
1. 正しい情報でログインできる
2. 間違ったパスワードではログインできない
3. 未入力時にエラーが表示される
```

内部では、

* テスト＝シナリオ
* 確認項目＝テストケース

として保存します。

「シナリオ」という用語を完全に消す必要はありませんが、UI上では「テスト」または「テスト内容」と併記する方が分かりやすいです。

例：

```text
テスト（シナリオ）名
```

---

# 4. データセットは上級者向け機能に寄せる

現在は「シナリオで使うテストデータ」というパネルが常に見えています。

業務上は重要ですが、すべてのテストで必要とは限りません。初めての利用者にとっては、何を入力する場所なのか分かりづらいです。

## 推奨

初期状態では折りたたみます。

```text
▸ テストデータを設定する（任意）
```

展開すると、

```text
ログインID
パスワード
対象URL
備考
```

などを入力できるようにします。

「scope」「case」「run」などの内部用語は一般利用者には見せない方がよいです。

現在のコードでは用途選択として、

* シナリオ用
* 共通
* ケース用
* 実行用

が表示されていますが、これは管理者または詳細設定用のUIに分離するのが適切です。

---

# 5. 保存処理を明確にする

現状は「シナリオを保存」というボタンがありますが、実際にはシナリオ、ケース、データセットなど複数の要素を保存します。

利用者にとっては、何が保存されるかが分かりにくいです。

## 推奨文言

```text
テスト全体を保存
```

保存前には変更件数を表示すると安心です。

```text
保存内容

シナリオ：1件
テストケース：5件
テストデータ：1件
```

保存成功後は次の行動を案内します。

```text
保存しました。

[続けて編集] [テストを実行する]
```

現在の「保存後は『テスト実行』から実行対象を選びます」という説明だけでは、もう一度タブを探す必要があります。直接遷移ボタンを出す方が自然です。

---

# 6. テスト実行画面は「設定」と「実行」を分ける

テスト実行には、少なくとも次の二段階があります。

1. 実行対象、環境、担当者を決める
2. 各項目の結果を入力する

これを同じ画面に詰め込むと、情報量が多くなります。

## 推奨フロー

### 実行準備

```text
実行名
対象テスト
環境
ビルド番号
担当者

[実行を開始]
```

### 実行中

```text
進捗 3 / 10

確認項目1
○ 合格
○ 不合格
○ ブロック
○ スキップ

実績結果
備考
証跡
```

実行開始後は、作成時の情報を編集する画面ではなく、**結果入力に集中できる画面**にしてください。

---

# 7. 証跡はテスト結果のすぐ近くに置く

現場では、結果と証跡は一組です。

そのため、証跡を別の大きな管理画面として見せるより、各結果の直下に置くのが自然です。

```text
結果：不合格

実績結果
ログイン後に500エラーが表示された

証跡
[ファイルを追加] [クリップボードから貼り付け]

画像サムネイル
```

証跡のファイル管理、バージョン、MIMEタイプなどは裏側で管理し、通常画面には出さない方がよいです。

---

# 8. 「手順書」と「テスト」の違いを明示する

現在は「手順書」が独立タブにありますが、一般利用者にはテスト手順との違いが分かりません。

画面に短い説明が必要です。

```text
作業手順

テストそのものではなく、環境準備、リリース作業、
事前確認などの作業手順と実施時刻を管理します。
```

また、名称を「作業手順」に変える方が、テストケース内の手順との混同を減らせます。

---

# 9. Excel取込は独立タブでなくてもよい

Excel取込は頻繁に使う主要機能ではなく、作成方法の一つです。

そのため、独立タブよりも「テスト設計」画面の作成メニューに含める方が自然です。

```text
＋ 新しいテスト

・画面で入力
・Excelから取り込む
・既存テストを複製
```

独立タブとして残す場合でも、何が取り込まれるのかを明記すべきです。

現在の説明はCasesとStepsシートを編集する内容ですが、初めて使う人には「Cases」「Steps」の意味が伝わりにくいです。

```text
Casesシート：確認項目の基本情報
Stepsシート：各確認項目の操作と期待結果
```

という説明が必要です。

---

# 10. 入出力は目的別に整理する

「入出力」という名称は技術的で、何ができるか分かりません。

中身を次の目的別に分けると分かりやすくなります。

```text
データを取り込む

・正式JSONを取り込む
・CSVを取り込む
・Markdownを取り込む

データを出力する

・テスト仕様書を出力
・実行結果を出力
・バックアップ用JSONを出力
```

「JSONエクスポート」も、目的に応じて名称を分けるべきです。

* バックアップを出力
* 他環境への移行データを出力
* テスト仕様書を出力

単にJSONと表示しても、現場利用者には用途が伝わりません。

---

# 11. 権限表示は操作に結び付ける

現在はヘッダーに「編集可」「閲覧のみ」が表示されています。これは改善されています。

ただし、閲覧のみの場合に入力欄や編集ボタンを表示したまま無効化すると、利用者は故障と誤解する可能性があります。

## 推奨

閲覧のみの場合は、画面上部に明確な案内を表示します。

```text
このプロジェクトは閲覧のみです。
編集するには管理者へプロジェクト割り当てを依頼してください。
```

編集ボタンは非表示にするか、無効化理由をツールチップで表示します。

---

# 12. エラー表示を利用者向けにする

コード上では、APIの例外メッセージをそのまま表示している箇所があります。

```ts
setError(reason instanceof Error ? reason.message : ...)
```

開発中は便利ですが、現場利用者には技術的すぎるエラーが出る可能性があります。

## 推奨構成

```text
処理を完了できませんでした。

シナリオの読み込みに失敗しました。
画面を再読み込みして、もう一度お試しください。

エラーID：REQ-12345
```

詳細なスタックやSQLエラーはサーバーログに残し、画面には出さないようにします。

---

# 13. 保存中・保存済み・失敗を常に見せる

自動保存や複数API処理があるため、利用者が現在の保存状態を把握できることが重要です。

```text
● 未保存
◌ 保存中...
✓ 保存済み 14:35
! 保存に失敗しました
```

特にテスト実行結果では、保存失敗を見逃すと業務上の問題になります。

保存失敗時はトーストだけではなく、対象行にも警告を残すべきです。

---

# 14. 画面の情報量を段階的に出す

現状は一画面に多数のフォーム、一覧、説明、ボタンが表示される傾向があります。

現場向けでは、最初に必要な情報だけを表示し、必要なときに詳細を開く方がよいです。

## 基本情報

* タイトル
* 操作
* 期待結果

## 詳細設定

* 目的
* 前提条件
* 優先度
* タグ
* フォルダ
* テストデータ
* 画像
* Markdown

このような段階表示にすると、初心者と上級者の両方に対応できます。

---

# 15. 用語を統一する

現状、次の用語が混在しています。

* ケース
* テストケース
* シナリオ
* テスト
* 手順
* 操作
* 確認項目
* データ
* データセット

画面ごとに言葉が変わると、同じものか別のものか判断しづらくなります。

## 推奨用語

| 内部概念      | 画面表示   |
| --------- | ------ |
| scenario  | テスト    |
| test case | 確認項目   |
| test step | 操作手順   |
| expected  | 期待結果   |
| data set  | テストデータ |
| run       | テスト実行  |
| evidence  | 証跡     |
| procedure | 作業手順   |

仕様書や管理者向け画面では、必要に応じて括弧内に内部名称を併記できます。

## 総評

現在のWeb版は、**機能不足よりも、機能をどう見せるかが課題**です。

裏側の機能は既に相当揃っています。
大きな再実装より、次の考え方で画面を整理する方が効果が高いです。

> 利用者には「テストを作る」「実行する」「結果を残す」だけを見せる。
> ケース、データセット、スナップショット、リビジョンなどの技術的概念は必要な場面だけ表示する。

この方針で整えると、専門のQA担当者だけでなく、開発者、運用担当者、業務担当者も使いやすいツールになります。
